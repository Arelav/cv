# Rules

- **Permission for tooling & scaffold:** Do not edit `biome.json`, ESLint config, `tsconfig.json`, `next.config.*`, or other generator / tooling defaults unless the user explicitly asked to change that file or category of settings. **Never** disable, downgrade, or override linter rules (new `overrides`, turning rules `off`) without **explicit user permission** — adjust the code to satisfy the linter instead. If the user did not ask to refactor the app’s original fetch, layout, or config patterns, do not rewrite them as part of another task; keep the smallest diff that fulfills the request.
- **No in-file linter suppressions without permission:** Do not add `biome-ignore`, `eslint-disable`, `@ts-expect-error`, `@ts-ignore`, or any comment/directive whose purpose is to silence a diagnostic, **unless the user explicitly authorized that suppression for that case**. Prefer fixing the code (rename types, refactor) instead of silencing.
- **Baseline when VCS exists:** If this project is under version control, compare against the initial commit (or the user-stated baseline) before large or sweeping changes, so you do not silently replace the generated app shape. This workspace may have no git history — then do not assume you may replace scaffolded structure without the user saying so.
- **Agent compatibility:** Project conventions live in `AGENTS.md` (root) and `.agents/` (`stack.md`, `rules.md`, `components.md`, `workflow.md`). Extend those files when adding durable guidance so every agent (Cursor, Claude Code, etc.) sees the same rules — do not rely on chat-only instructions.
- **Type imports:** Do not use `import type * as …` (namespace type imports) unless the user explicitly allowed it. Use named imports: `import type { Foo, Bar } from "…"`.
- **This repo is the Next.js app (`cv`), not Go:** When editing here, use TypeScript/React patterns and this file layout. Do not default to `cv-api` conventions, package names, or idioms unless you are explicitly changing the backend.
- **Backend failure → fix the backend:** If the problem is a server error, wrong response, or bug in **cv-api** (Go), fix it in **`cv-api`**. Do not change **`cv`** (types, fetch UI, refactors) as a substitute unless the user asked for frontend work or the frontend is demonstrably wrong.
- **Fetch `Response` naming:** Do not name the result of `fetch()` `res`. Use `response` (or another explicit name).
- **Comments:** Do not add JSDoc, `//`, or block comments that restate the code, narrate obvious steps, or duplicate what types already say. Comment only when behavior is genuinely non-obvious without it.
- **Next.js + backend GETs:** Before changing fetch/error patterns, read `node_modules/next/dist/docs/01-app/01-getting-started/06-fetching-data.md` and `10-error-handling.md`. Same on the web: [fetching data](https://nextjs.org/docs/app/getting-started/fetching-data), [error handling](https://nextjs.org/docs/app/getting-started/error-handling). In Server Components: plain `fetch`, `await response.json()`, then `if (!response.ok)` and return UI — no `try/catch` for the happy path, no fetch wrapper. On `!response.ok`, render `*FetchError` with a generic message (do not pass through HTTP status codes or backend error bodies). `API_URL` in env (e.g. `.env.local`).
- Prefer Server Components; use `"use client"` only when necessary
- No `useEffect` for data fetching
- All API calls go to the Go backend (`cv-api`)
- Never ignore explicit instructions from the user
- Mobile-first: write base styles for mobile, use `sm:` / `md:` / `lg:` to scale up
- Use semantic HTML: `<main>`, `<nav>`, `<header>`, `<footer>`, `<section>`, `<article>`, `<aside>`, `<h1>`–`<h6>` in correct hierarchy
- Accessibility: meaningful `alt` text, `aria-label` where needed, keyboard-navigable interactive elements, sufficient color contrast, no `<div>` for interactive elements
